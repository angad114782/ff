# 11. Authentication & Security

## Authentication
- **Passwords:** scrypt (random 16-byte salt, 64-byte hash), constant-time compare. Minimum 8 characters.
- **Session:** JWT (HS256, `JWT_SECRET`) in the `ff_session` cookie — `HttpOnly`, `SameSite=Lax`, `Secure` in production, 12 h (`SESSION_HOURS`).
- **Per-request revalidation:** the user row is loaded every request; the token's `v` must equal `users.token_version`, the account must be `active`. Password change/reset and deactivation bump `token_version`, so stolen/old cookies stop working immediately. After a self-service password change the current device gets a fresh cookie.
- **Login hardening:** rate limit 10 attempts / 15 min / IP on login and forgot-password; identical error for unknown email vs wrong password; a dummy hash is verified for unknown emails to even out timing.
- **Forgot password:** always returns `{ok:true}`; creates a `reset_request` log for existing active salesmen. An admin sets a new password.

## Authorization
`requireAuth` (any user) and `requireRole('admin')`. Admin area is mounted at `/api/admin`; media writes are admin-only. The client's `RequireRole` is a convenience only.

**Data exposure:** salesman responses are built without purchase price, vendor name/group/contact, external item id (`stockMapper.mapItem`); tested.

## Secrets
- BC client secret: AES-256-GCM, key `APP_ENCRYPTION_KEY` (32 bytes base64), stored as `enc:v1:…`; write-only over the API.
- Production needs only `MONGODB_URI`; `JWT_SECRET` / `APP_ENCRYPTION_KEY` are generated into the database unless set as env vars (set them to keep keys out of the DB).
- First admin: one-time setup screen, closed for good once an admin exists (race-safe, rate-limited).
- Dev secrets are generated to `server/data/dev-secrets.json` (0600, gitignored).
- Rotating `JWT_SECRET` signs everyone out. Rotating `APP_ENCRYPTION_KEY` requires re-entering the BC secret.

## Web hardening
- `helmet` headers incl. a CSP (`default-src 'self'`; images/media allow `blob:`/`data:` for the scanner and previews).
- CSRF: `SameSite=Lax` + `originCheck` middleware rejects state-changing requests whose `Origin` host differs from `Host` (allow extras via `CLIENT_ORIGIN`).
- JSON body limit 100 kB; uploads: MIME allowlist, ≤100 MB, ≤10 files, random server filenames, served inline with the stored MIME and `nosniff`.
- Input validation on every write; BC URL path segments restricted to `[A-Za-z0-9._-]`.
- SQL always parameterised.
- The PWA service worker never serves the app shell for `/api/*`.

## Known gaps / recommendations
- No MFA; no per-account lockout (only IP rate limiting).
- Audit trail covers salesman logins/searches only — not admin changes (config, user management).
- Rate limiting is per process (in-memory); use a shared store if you run several instances.
- Stored credentials are AES-256-GCM encrypted, but with the default setup the key sits in the same database; use `APP_ENCRYPTION_KEY` env to separate them. Enable database encryption at rest (Atlas does).
- Upload content isn't scanned (type is trusted from the declared MIME).
- HTTPS is mandatory in production (Secure cookies, `upgrade-insecure-requests` CSP).
- Admin routes are protected by the session only — consider IP allow-listing or SSO for the admin role.
