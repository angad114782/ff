## Key decisions
- **Server is a BC proxy.** The browser never sees BC credentials or tokens. BC OAuth client-credentials token is cached in memory and refreshed on 401.
- **No stock database.** Stock is always read live from BC; the app stores only users, logs, media and settings.
- **MongoDB** holds everything the app stores, including uploaded media (GridFS) and its own secrets, so a deployment needs only `MONGODB_URI`. Stateless app instances can scale out.
- **Cookie sessions (JWT in HttpOnly cookie)**, user reloaded from DB per request so deactivation / password change take effect instantly (`token_version`).
- **One origin in production.** Express serves `client/dist`; in dev Vite proxies `/api` → `:4000`.
- **Role filtering on the server.** `stockMapper.mapItem(row, { admin })` omits cost/vendor data for salesmen.

## Search flow
1. Client `GET /api/stock/search?q=…` (typed) or `?barcode=…` (scanned).
2. Server builds BC body (`searchText` or `qrCode`), calls BC, unwraps the double-encoded response, maps rows to summaries, adds vendor stock and a total when there are several rows, logs the search if the caller is a salesman.
3. One hit → client opens `/…/item/:code`; several → list; none → "not found".
4. Detail: `GET /api/stock/item/:code` → BC search by item no, exact match, map, add vendor lookup and `totalStock` (our stock + vendor stock).

## Deployment
Single container (see `Dockerfile`): builds the client, runs `node server/src/index.js`, data in `/data`. Needs HTTPS in front (Secure cookies) and `TRUST_PROXY`.
